# Design: 钉钉集成——工单创建后自动拉群

## Problem Statement

工单创建后，系统内通知不可达：法务 BP 不会立刻看到新工单，处理时效慢。需要钉钉群即时触达工单流程中的人。每个法务 BP 有固定工作范围（如彭宇欣负责知识产权与数据合规），工单经意图识别匹配相应 BP，**创建时自动指派并拉群**；工单转派时新 BP 自动进群。首条消息为纯文字（工单标题/风险/提出人），不含链接。

## Demand Evidence

- 用户确认现状痛点：**"系统内通知不可达"**（工单从创建到法务 BP 接手，最疼的一环是通知不到人）
- 定位确认：**"企业内部落地"**——让团队真正用起来，优先把流程跑通
- 凭证已就绪：原企业内部应用 AgentId / Client ID / RobotCode / Client Secret（客户端凭证换 access_token 的标准链路成立）

## Status Quo

现状代码已存在完整 Mock 骨架（[adapter.interfaces.ts](LegalPlatform/api/src/modules/project/adapters/adapter.interfaces.ts)）：

- `DingTalkAdapter` 接口：`createGroup(members, title)` + `sendNotification(chatId, msg)`，绑定 `MockDingTalkAdapter`（只打日志）
- [project.service.ts:113-126](LegalPlatform/api/src/modules/project/project.service.ts#L113-L126)：工单创建后已调用拉群，但成员是占位符 `['业务人员', 'Pending BP']`，群是假的
- 升级风险/已回传已有 3 处通知点挂好 `dingtalkChatId`（Mock 群）
- User 表**没有手机号/钉钉字段**；seed 账号 `displayName` 是 `'法务BP-张三'`（带角色前缀，非真实姓名）

## Target User & Narrowest Wedge

**目标用户**：法务 BP（工单处理人）+ 业务提出人（creator）+ 法务负责人（审核兜底）。

**最小版本**（用户确认）：**拉群 + 首条消息**——真群建好、机器人发纯文字消息（工单标题/风险/提出人）；转派时自动加人；升级/回传沿用现有通知点。不做双向消息、不做审批流、不带链接。

## Constraints

- 企业内部应用凭证：Client ID (AppKey) + Client Secret → `gettoken` 换 access_token
- 建群接口需传成员 **userid 数组**；`RobotCode` 让机器人自动进群并发首条消息（`/v1.0/robot/groupMessages`）
- 钉钉后台权限：通讯录部门成员读权限（建群/通讯录必需）；「企业员工手机号信息」权限（可选，用于 mobile 对照）
- 现有工程约束：失败不阻断工单创建（已有 try/catch 模式）、凭证走 .env 不落 git

## Premises

1. **P1 通讯录同步绑定**（用户已确认）：配置期管理端一键同步钉钉通讯录 → 按真实姓名自动匹配系统用户 → 匹配失败手动下拉绑定 → User 表写入 `dingtalkUserId`（+`phone` 副产物）。运行期建群直接传 userid，不经过 getbymobile 手机号查询。
   **同步算法**：① `topapi/v2/department/list`（或 listsub）枚举部门树 → ② 逐部门调 `topapi/v2/user/list` 分页（size=100，游标 next_cursor 直到 has_more=false）→ ③ **按 userid 去重**（跨部门成员重复出现）→ ④ 按真实姓名匹配系统用户，**匹配到多个候选（重名）→ 落手动绑定**。失败重试 2 次，超时 10s。
2. **P2 数据规范化 + BP 工作范围**：seed 账号 `displayName` 从 `'法务BP-张三'` 规范化为真实姓名（**已确认：法务 BP = 彭宇欣**；其余账号待补齐）（姓名匹配的前提）；User 表加字段；**BP-领域映射表**（彭宇欣 → 知识产权/数据合规）配置在管理端成员管理页，与通讯录同步页合一。
3. **P3 失败容忍 + 凭证安全**：拉群/发消息失败不阻断工单创建，失败记录到工单事件；未绑定成员的 userid 跳过并事件记录；凭证走 .env。**token 缓存**：进程内存缓存 access_token，按 `expires_in` 提前 5 分钟刷新，遇 401 自动重试一次（单实例内部工具足够，多实例部署再升级）。
4. **P4 同步时序**：配置期同步是管理端手动触发的（一次性），运行期建群同步 await（带超时保护），先不做消息队列（跑通优先）。
5. **P5 幂等 + 转派加人**：create 是唯一建群入口（重复提交 = 新工单新群，天然幂等）；建群响应丢失重试时以工单事件记录尝试，群名带工单号（`工单#<id> <标题>`）便于人工分辨清理。**工单转派（update legalBpId 变更）→ 调钉钉群加人接口（adapter 新增 `addMember(chatId, userId)`）把新 BP 拉进群**。

## Approaches Considered

### Approach A: 通讯录同步绑定（推荐）
- 配置期：管理端「成员管理」页一键同步钉钉通讯录 → 姓名自动匹配 + 手动兜底 → 绑定 dingtalkUserId
- 运行期：建群传 userid 数组（直接取库，0 次额外 API）
- Effort: M / Risk: Low
- Pros: 运行期零查询；userid 直传不依赖 getbymobile 单独权限；数据自愈（成员变动再同步一次）
- Cons: 需要做成员管理页面（一次性成本）；姓名匹配依赖 displayName 规范化
- Reuses: 现有 DingTalkAdapter 接口 + createGroup 调用点 + dingtalkChatId 持久化

### Approach B: 手机号主链路（getbymobile）
- 系统里填手机号 → 拉群时逐个 `getbymobile` 查 userid
- Effort: S / Risk: Med
- Pros: 不需要同步页面，接口简单
- Cons: 手机号还得手工填（数据源问题绕不开）；每次拉群 N 次额外 API；需要单独申请「根据手机号姓名获取成员信息的接口访问权限」（非默认）；手机号隐藏/离职用户查不到

### Approach C: 双通道
- 同步绑定为主 + 绑定失败但有手机号的用 getbymobile 兜底
- Effort: L / Risk: Med
- Pros: 最健壮
- Cons: 实现量最大，两条链路都要测；对"跑通优先"属于过度设计

## Recommended Approach

**Approach A（通讯录同步绑定）**。理由：钉钉通讯录 `user/list` 一次拉全量（userid/name/mobile），直接拿 userid 建群——手机号查询是绕路（它恰恰需要系统先有手机号）。同步绑定一次配置长期有效，运行期建群 1 次 API 调用，最符合"企业内部落地、跑通流程"的定位。

**关键决策点**：
- **成员解析规则（v1）**：creator（提出人）必在 + 意图识别匹配的 BP（`legalBpId` 指派）→ 最终数组按 userid **去重**（BP 未指派/未匹配时群内仅提出人 + 事件记录）。v1 **不拉审核人**（Project 无审核人字段，避免引入 reviewerId 的指派逻辑）。**首条消息的"提出人"显示 requesterName（自由文本），群成员 = creator（FK）**——他人代提交时真实提出人不在群，v1 接受
- **意图识别作用范围（评审 N1 裁决）**：领域匹配 + 拉群**只在 legalbp 路由（P0/P1）执行**——P2（llm）工单保持现有"AI 处理、不打扰 BP"语义，不匹配不拉群；P2 升级为 legalbp 时**补建群**（复用完整匹配链：领域解析→指派→建群，见工程评审决策 #1）
- **领域来源（工程评审决策 #10）**：技能 group 优先（已选技能时确定性 100%）→ LLM 标签兜底 → 未匹配走兜底阶梯
- **意图识别扩展**：LLMRiskService 在风险分级（P0/P1/P2）同时输出**领域标签**（复用技能库 6 领域：合规法务/合同与交易/劳动法务/争议法务/法律研究/知识运营）→ 按 BP-领域映射表匹配 → 创建时写入 legalBpId；**映射表 key 钉死为 6 领域白名单（评审 N6 裁决），LLM 输出非白名单值按未匹配处理**（示例：彭宇欣 → 合规法务，其知识产权/数据合规归入该组）
- **匹配失败兜底（评审 N4 裁决）**：legalbp 工单领域匹配失败/无映射 → **兜底拉法务负责人（legal_lead，若已绑定 userid）**，避免"最该人工处理的工单群里无人"；兜底也失败才群仅提出人 + 事件记录
- **转派加人（评审 N2 裁决）**：**transfer()（POST :id/transfer）与 update()（PATCH :id）两处共用检测**（任一修改 legalBpId → 触发 `addMember(chatId, newBpUserId)`），不能只挂一处；新 BP 未绑定 userid → 跳过 + 事件记录（评审 N5）；加人失败事件记录；与 transfer() 现有 sendNotification 并存（通知保留，加群新增）；**addMember 接口随建群接口回退（场景群与普通群 v2 加人接口不同）**
- **全员未绑定**：解析后 userid 数组为空 → 跳过建群 + 工单事件 `全员未绑定钉钉，请人工建群`
- **部分未绑定**：跳过 + 工单事件记录（列出未绑定的姓名），不阻断建群
- **通知降级**：`dingtalkChatId` 为空（拉群失败）时，升级/回传 3 处通知点静默跳过（与现有 null 判断一致）
- **首条消息可观测**：首条消息发送失败同样写工单事件（`群已建但首条消息发送失败`），避免"群建成了但没消息"不可见
- **重试上限**：建群响应丢失 → 重试 **1 次**（不无限重试刷群）；仍失败按拉群失败处理
- **存量数据**：真适配器上线前，清理存量工单的 `DING-MOCK-*` chatId（置空），避免对假群发通知
- 建群 API：优先「创建普通群 v2」（用户提供文档），联调失败回退场景群 `scenegroup/create`（两者都支持 robotCodes 机器人进群）；首条消息走 `/v1.0/robot/groupMessages`（纯文字，无链接）
- 群名：`工单#<id> <标题>`（便于识别与重复群人工清理）
- 事件文案：`钉钉群已创建`（不再标"模拟"）；拉群失败 `钉钉拉群失败，请人工建群：<原因>`
- 配置：`DINGTALK_APP_KEY / DINGTALK_APP_SECRET / DINGTALK_AGENT_ID / DINGTALK_ROBOT_CODE` 进 .env + .env.example 占位（无链接配置项——首条消息纯文字）

## Engineering Review Decisions（/plan-eng-review 2026-08-05，外部声音采纳）

1. **升级补建群跑完整匹配链**：P2→legalbp 升级路径（createMessage）复用"技能/LLM 领域解析 → 指派 BP → 建群"整条链，而非只调建群函数（否则最紧急工单群里无 BP 认领）
2. **legalBpId 变更检测 3 处**：transfer() + update() + **reply() 回传认领**（回传也写 legalBpId，须触发 addMember）；共用检测函数
3. **update() 补角色校验**：legalBpId 只能设为 legal_bp/legal_lead（现状 PATCH 无校验，否则钩子会把 business 用户拉进法务群）
4. **update() route 变更 llm→legalbp 也补建群**（不只 createMessage 升级路径）
5. **群名截断**：`工单#<id前6位> <标题前12字>`，总长 ≤20 字（钉钉群名限制）
6. **ownerUserId 定义**：建群必填参数 = creator（已绑定 userid 时），否则取 BP；都未绑定 → 不建群
7. **机器人进群时序 spike 验证**：robotCodes 进群可能非即时生效，首条消息时序列入联调 spike
8. **失效绑定处理**：同步时按 userid 更新已有绑定、不自动解绑（保守）；建群失败含坏成员 → 剔除坏成员重试 1 次，仍失败按拉群失败处理
9. **无法务成员不建群**：解析后无法务角色成员（BP/负责人）→ **不建群** + 事件"请人工建群"（替代原"群仅提出人"——单成员群无触达价值且钉钉可能拒绝）
10. **领域来源：技能 group 优先 + LLM 兜底**：建单已选技能 → 用 skill.group 定领域（确定性）；无技能 → LLM 领域标签；两者皆无 → 未匹配走兜底阶梯
11. **LLM 双输出容错**：风险+领域双标签输出；风险部分解析失败 → 默认 P1/legalbp（沿用现有安全优先）；领域部分失败 → 未匹配
12. **同步快照表**：新增 `dingtalk_contacts`（同步结果落库，手动绑定可搜索快照；下次同步更新快照、对比现网）
13. **spike 先行**：联调 spike（通讯录权限验证 + 建群 v2 参数 + 机器人进群时序）排在任何页面/服务开发之前
14. **升级路径异步**：create() 建群同步 await（已裁决）；createMessage 升级路径建群 fire-and-forget（不挂住 SSE 聊天）
15. **转派只加人、旧 BP 留群**（用户裁决 T3）：不做移除接口，群内事件提示可见
16. **多 legal_lead / 同领域多 BP**：兜底/匹配取第一个已绑定 userid 的（v1 简单规则，负载均衡 v2）
17. **mock 事件文案区分**：`钉钉群已创建（模拟）` vs `钉钉群已创建`，按 DINGTALK_MOCK 开关

## Success Criteria

1. 配置期：管理端「成员管理」页同步钉钉通讯录（部门枚举→分页→去重→匹配，重名落手动）→ 系统用户按姓名匹配绑定（匹配失败可手动绑定）；BP-领域映射表可配置
2. 建工单（legalbp 路由）→ 意图识别输出领域 → 匹配 BP → 指派 legalBpId → 钉钉群自动创建（提出人 + 法务 BP），机器人自动进群；匹配失败 → 兜底拉法务负责人（已绑定），仍失败 → 群仅提出人 + 事件记录
3. P2（llm）工单不拉群（保持"AI 处理、升级才通知 BP"语义）；P2 升级 legalbp → 补建群（复用同一函数）
4. 建群后机器人发首条消息（纯文字）：工单标题 + 风险等级 + 提出人（requesterName）
5. 转派（transfer() 或 update() 修改 legalBpId）→ 新 BP 自动进群；新 BP 未绑定 → 跳过 + 事件记录
6. 未绑定成员不阻断建群（跳过 + 工单事件记录，列出未绑定姓名）
7. **全员未绑定 → 跳过建群 + 事件"请人工建群"**
8. 拉群失败不阻断工单创建（沿用 try/catch 模式，新增事件记录）；建群重试上限 1 次
9. 升级/回传通知发送到真实群（复用 dingtalkChatId；chatId 为空时静默跳过）
10. 存量 DING-MOCK-* chatId 已清理；凭证在 .env，.env.example 有占位，无明文入库
11. 管理端成员管理页：同步/绑定/BP 领域映射/拉群失败计数可用
12. 单元测试：适配器（token 缓存与 401 刷新/通讯录同步去重/建群/加人/发消息 mock）+ 工单创建链路（legalbp 匹配 BP、P2 不拉群、升级补建群、成员解析去重跳过、全员未绑定）+ 转派加人
