## Problem Statement

两个架构层面的待决策项：
1. **合同文件存储**：当前文件存本地磁盘（`api/storage/contracts/`），DB 存元数据（ContractFile 表）——本地磁盘无备份，机器故障文件即丢失
2. **Project 模型职责膨胀**：Project 表同时承载 consult/contract 等多业务类型，每加类型加列，字段持续膨胀（如 contractTemplateSlug）

## 决策（已确认 2026-08-03）

### 决策 1：文件存储 = 本地磁盘 + 备份策略（不存数据库）

**不采用数据库 BLOB** 的理由：
- MySQL 不是文件系统——20MB 二进制进 InnoDB，缓冲池/备份/主从复制全遭殃
- 合同文件是交付物，DB 存"文件在哪"（元数据）即可，文件本体放存储层
- 行业标准：文件 → 对象存储，DB → 元数据（当前 ContractFile 表已是此模式）

**方案**：
- 保持现状（磁盘 + ContractFile 元数据）
- 补充**备份策略**（MVP 可执行）：
  - `api/storage/` 目录纳入备份计划：**每周全量压缩归档 + 每日增量**，保留 4 周
  - 提供备份说明文档（备份命令 + 恢复步骤）
- **v0.1.0 迁移 OSS**：`ContractFileService` 的读/写已隔离在 service 内，替换实现即可，DB 表结构不变
- **敏感文件防护**（工程评审发现）：`api/.gitignore` 忽略 `storage/` + `.tmp/`（合同文件绝不进 git 仓库）

### 决策 2：Project 模型 = 维持单表 + 预留 `extra Json` 列

**维持单表**（consult/contract 共用）的理由：
- "我的记录"跨表查询成本高（多表需 UNION）
- 当前已用"类型特有数据外置关联表"（ContractFile）缓解膨胀
- MVP 阶段字段数量可控

**预留扩展**：
- Project 加 `extra Json?` 列：未来 research/draft 的类型特有字段进 JSON，不再每类型加列
- 现有 contractTemplateSlug 保持独立列（已是既有字段，查询友好）

## 实施步骤

1. Prisma：Project 加 `extra Json?` 列 → migrate（`add_project_extra_json`）
2. 备份文档：`api/storage/README.md`（备份命令 + 恢复步骤 + OSS 迁移指引）
3. 无前端改动
