## Problem Statement

业务端（包正和等销售人员）需要一条轻量路径发起法律咨询——用自然语言描述问题 → 系统自动判断严重程度 → 常规问题 AI 即时答复 / 高风险问题自动升级法务BP处理 → 结果回到原会话。整个流程不能超过 CRM 内部流转的时间（当前 0.5~1 天），常规问题应在 1 分钟内返回结果。

## Demand Evidence

- **包正和**（华北IU销售）：客户现场等法务意见，打开钉钉→CRM→邮件来回找历史答复，"能在业务端直接得到答案，不用切系统就行"
- **彭宇欣**（法务BP）：每天处理大量常规合规咨询（"促销活动合规吗"、"这个条款能改吗"），80% 是标准答案，"P2 自动处理掉我就不用看了，P1 工单进来至少有 AI 初稿"
- 整个链路在工单模块设计文档中已有消息流和状态机基础，本模块绑定"业务咨询"这一具体场景

## Status Quo

当前业务人员通过 CRM 提交合同/咨询请求 → 法务在 CRM 里回传意见。非合同类的 ad-hoc 咨询（"这个活动合规吗"）只能在钉钉或微信上私聊法务BP，无记录、无追踪、无复用。

## Target User & Narrowest Wedge

**第一手用户**：包正和（业务端发起咨询）→ AI 直接答复（P2）/ 彭宇欣法务处理（P1）→ 包正和收到回传

**最窄可用版本**：
1. 包正和在 `/business/consult` 输入问题 → 自动风险判定
2. P2：AI 四段式答复，SSE 流式渲染，1 分钟内出结果
3. P1：自动创建工单 → 包正和看到"已通知法务BP" → 彭宇欣在法务端处理回传
4. 包正和在 `/business/records` 看到完整历史和回传结果

## Constraints

- **复用而非重建**：数据模型复用工单模块的 Project + ProjectMessage 表，P2 也创建工单（route=llm），统一审计和记录查询
- AI 引擎统一通过 Codex CLI（`codex exec`），SSE 流式输出
- 钉钉/CRM 采用 Adapter 模式 Mock 实现
- 技术栈不变：NestJS + Prisma + MySQL + Vue 3
- 风险判定关键词表与工单模块共用（同一个 RiskService）

## Premises

1. ✅ P2 也创建工单（kind=consult, route=llm, status 自动→已回传）——统一审计、统一"我的记录"
2. ✅ MVP 阶段 P2 答复底部加"升级人工处理"按钮——route llm→legalbp，AI 胡说八道时用户有逃生通道
3. ✅ 业务端对话式交互——类 ChatGPT，SSE 流式渲染 AI 答复，支持多轮对话
4. ✅ 风险判定与工单模块共用同一个 RiskService
5. ✅ P2 流结束后一次性落库（与工单模块工程评审决策一致）

## Approaches Considered

### Approach A: 复用工单模块（轻量业务层）✅
在已有 ProjectModule 之上加一个薄的 ConsultModule，只做三件事：创建咨询工单 + 触发 AI 对话 + P2 升级请求。不新建数据库表，不重复实现消息流和状态机。

- Effort: M（人~1.5天 / CC~20min）
- Risk: Low
- Pros: 零新表，审计统一，消息流复用，升级路径天然通畅（只改 route 字段）
- Cons: Project 表的 consult 特定字段（如四段式答复结构）与 contract/research 混在一起，后续字段多了需要区分
- Completeness: 9/10

### Approach B: 独立咨询模块（新表新服务）
新建 Consultation 表 + ConsultationMessage 表，独立 API 前缀 `/api/consult`，独立前端。P2 存咨询表，P1/P0 创建时转写为 Project。

- Effort: L（人~3天 / CC~40min）
- Risk: Med
- Pros: 数据模型完全贴合业务场景；P2 和工单逻辑隔离
- Cons: 两套表结构，"我的记录"需要跨表 UNION 查询；升级时需要数据迁移；代码重复
- Completeness: 7/10

## Recommended Approach

**Approach A**。工单模块已经设计了 route 字段（llm / legalbp）和 kind 字段（consult / contract / research / draft），业务咨询恰好是 kind=consult 的一种 route 场景。额外建表带来的"我的记录"跨表查询和维护成本远大于混用 Project 表的代价。

### 2. API 设计

所有端点挂载在 `/api/consult`，底层调用已有 ProjectService + CodexService。

```
# 发起咨询（创建工单 + 触发 AI）
POST   /api/consult
  Body:   { query: string, skillId?: string }
  Logic:
    1. RiskService.assessRisk(query) → { risk, route }
    2. ProjectService.create({ kind: consult, route, risk, title, creatorId, ... })
    3. ProjectService.createMessage({ role: user, text: query })
    4. If route=llm:
       → ProjectService.createEvent("系统判定 P2 常规风险，AI 正在生成答复…")
       → CodexService.executeStream(prompt) → SSE 推前端
       → 流结束: ProjectService.createMessage({ role: assistant, text: fullAnswer })
       → ProjectService.updateStatus(已回传)
       → SSE final event: { projectId, status: "已回传" }
    5. If route=legalbp:
       → ProjectService.createEvent("系统判定 P1/P0 风险，已创建工单通知法务BP")
       → DingTalkAdapter.sendNotification(...)
       → HTTP response: { projectId, risk, status: "分析中" }
  Response (P2): SSE 流
  Response (P1/P0): { projectId, risk: "P1"|"P0", status: "分析中" }

# P2 升级为人工处理
POST   /api/consult/:id/upgrade
  Logic:
    1. 校验: project.kind=consult, project.route=llm, project.status=已回传
    2. ProjectService.update({ route: legalbp, status: 待复核 })
    3. ProjectService.createEvent("用户申请升级为人工处理")
    4. DingTalkAdapter.sendNotification(...)
  Response: { projectId, status: "待复核" }

# 获取我的咨询记录列表
GET    /api/consult/mine?status=&page=&size=
  Logic:
    1. 从 JWT 取当前用户ID → 查询 creatorId 匹配的 consult 类型工单
    2. ProjectService.list({ kind: consult, creatorId, status, page, size })
    3. include creator + legalBp（与工单模块一致的预加载优化）
  Response: { items: Project[], total, page, size }

# 获取单个咨询详情（含完整对话历史）
GET    /api/consult/:id
  Logic:
    1. ProjectService.findOne(id) include messages + events
    2. 权限校验: 只能看自己创建的（creatorId = currentUser）或法务端可看自己处理的
  Response: Project with messages[]
```

### 5. 风险判定（LLM 意图识别）

> 工程评审决策 #3：关键词匹配→LLM意图识别。每次咨询先调一次轻量分类 prompt（~1s），准确判断用户真实意图后再决定路由。

```typescript
// api/src/common/services/llm-risk.service.ts
@Injectable()
export class LLMRiskService {
  constructor(private readonly codexService: CodexService) {}

  async assess(query: string): Promise<{ risk: RiskLevel; route: ProjectRoute }> {
    const prompt = `判断以下法律咨询问题的风险等级，只回复一个标签（P0/P1/P2）：

P0（紧急）：涉及刑事犯罪、监管执法调查、紧急法院禁令、重大安全事故
P1（重要）：涉及无限责任、数据出境、跨境传输、个人信息保护、诉讼仲裁、并购股权、竞业限制
P2（常规）：其他一般法律问题，合规咨询，合同条款询问，政策了解

用户问题：${query}

风险等级：`;

    const result = (await this.codexService.execute(prompt, { maxTokens: 5 })).trim();
    const risk = result.includes('P0') ? 'P0' : result.includes('P1') ? 'P1' : 'P2';
    const route = risk === 'P2' ? 'llm' : 'legalbp';
    return { risk, route };
  }
}
```

### 6. 四段式 Prompt 模板

CodexService.execute() 使用的 business consult prompt 模板：

```markdown
## Role
你是一名企业法务顾问，为业务人员提供法律咨询答复。

## Output Format（严格按四段式输出）
### 核心结论
一句话总结你的法律判断。

### 重点风险
列出 2-3 个最关键的法律风险点，每条不超过两句话。

### 建议动作
给出具体可执行的下一步行动建议。

### 需补充确认
列出需要进一步确认的事实或信息（如有）。如果信息足够，写"无，以上判断基于现有信息可执行"。

## Rules
- 不引用具体法条号（除非用户追问）
- 只说你能确定的事，不确定的事项放在"需补充确认"
- 如果问题超出法务范围（如税务、财务），明确告知并建议联系对应部门
- 每条答复末尾追加免责声明："> ⚠️ 本答复由AI生成，不构成正式法律意见。如需正式法务意见，请联系法务BP确认。"

## 免责声明（前端固定展示）
每条 AI 答复底部渲染灰色小字：
"本答复由AI生成，仅供参考，不构成正式法律意见。涉及重大决策请咨询法务BP。"
```

#### SSE 流式渲染细节

- 前端 EventSource 或 fetch + ReadableStream 读取 `/api/consult` SSE 响应
- 每个 SSE chunk 包含 `text` 增量 → 前端追加到当前 assistant 消息
- 流结束收到 `[DONE]` 事件 → 前端标记该消息 complete，追加 projectId 到页面状态
- 升级按钮在 assistant 消息 complete 后出现
- 渲染过程中 textarea 保持可用（用户可以同时输入下一条消息，但发送按钮禁用直到流结束）

## Success Criteria

- [ ] 包正和以 business 角色登录 → `/business/consult` → 输入合规问题 → SSE 流式渲染 AI 四段式答复（P2 场景，~30s 内完成）

- [ ] 包正和进入 `/business/records` → 看到自己的所有咨询历史 → 按状态可筛选 → 点击进入完整对话
- [ ] P2 工单 route=llm, status=已回传 → "我的记录"中可见且可继续追问
- [ ] P1/P0 工单回传后 → 包正和在"我的记录"中看到更新状态和法务答复

## Engineering Review Decisions（/plan-eng-review, 2026-08-02）

| # | 决策 | 影响 |
|---|------|------|
| 1 | 多轮对话通信：POST 提交追问 + SSE 响应。每条消息一问一答，HTTP 天然双向 | 设计文档明确每轮通信模式 |
| 2 | P1 业务端可见性：只显示"已通知法务BP"，AI 初稿和处理过程对业务端不可见 | 设计文档修正 P1 消息流描述 |
