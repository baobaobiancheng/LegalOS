## Problem Statement

现有 3 个内置合同模板（渠道合作/技术服务/保密协议）是通用假模板，与公司实际业务脱节。`合同模板/` 目录下有法务平时使用的真实模板（百融AI服务协议、保密协议 V4.5、技术开发合同等），包含公司标准条款口径与固定排版格式。目标：
1. 用 3 个真实模板替换内置模板
2. 定义每模板对应的**合同要素**（生成草稿的输入表单）
3. **草稿导出 Word 时字体/排版/大小与模板一致**（当前导出用微软雅黑通用样式，与模板的楷体系不一致）

## Demand Evidence

- 法务平时以 `合同模板/` 下 docx 为基准起草合同，格式（楷体正文/Arial 西文/标准页边距）是公司对外合同的标准
- 业务端生成的合同草稿若格式与公司标准不一致，法务仍需重排版，AI 提效打折扣
- 模板正文含公司已审定的条款口径（如 AI 服务协议的知识产权、保密约定），AI 按此生成可复用审定口径

## Status Quo

当前：ContractTemplate 表存通用 prompt（3 个假模板），`markdown-to-docx.ts` 用微软雅黑通用样式导出，草稿章节由 AI 自由发挥，与公司模板结构/格式均不一致。

## Premises（已确认 2026-08-03）

1. ✅ 替换内置 3 模板为：**百融AI服务协议【主协议】** + **保密协议 V4.5（机构合作端）** + **联合建模项目-技术开发合同-通用版**；旧模板保留在 DB（isActive=false），历史工单不受影响
2. ✅ 每模板定义一套**合同要素 schema**（表单字段从模板正文提取），前端按 schema 动态渲染表单
3. ✅ 导出方案 **A：前端 markdown-to-docx 样式参数化**——模板样式存 JSON（字体/字号/标题/页边距），前端按样式生成 docx
4. ✅ 模板 docx 源文件复制入 `api/storage/contract-templates/{slug}/` 存档

## Approaches Considered

### Approach A: 前端样式参数化 ✅
模板样式提取为 JSON 存 ContractTemplate.style，前端 markdown-to-docx 接收样式参数生成 docx。
- Effort: M（人 ~1.5 天 / CC ~20min）
- Risk: Low
- Pros: 改动最小（前端 1 文件 + 样式配置）；样式完全可控；现有下载链路（DownloadMenu）不变；docx 库原生支持 eastAsia 中文字体
- Cons: 样式保真依赖解析质量（一次性提取，人工校正一次）
- Completeness: 9/10

### Approach B: 后端 docx 生成
api 装 docx 库，新增导出端点按模板样式生成。
- Effort: L（人 ~2.5 天 / CC ~40min）
- Risk: Low-Med
- Pros: 后端统一生成，前端零逻辑
- Cons: 新增后端依赖 + 下载链路变化（SSE 消息下载需先落盘再取）；与现有前端 DownloadMenu 重复
- Completeness: 8/10

### Approach C: 模板 docx 底稿 + 占位符替换
模板 docx 做底稿，AI 内容替换占位符。
- Effort: XL（人 ~5 天 / CC ~1h）
- Risk: High
- Pros: 保真度最高（模板原始格式）
- Cons: AI 自由文本 vs 固定模板结构难对齐；docx 库是生成器非编辑器；占位符维护成本高
- Completeness: 10/10 但 MVP 过度

## Recommended Approach

**Approach A**。导出 docx 的格式一致性 = 字体（楷体中文 + Arial 西文）+ 标题（加粗/居中）+ 页边距 + 行距。这些是有限样式参数，用 JSON 配置 + 前端 docx 库生成完全可控，无需后端参与。

### 4. 生成 prompt（从模板正文提炼）

每模板 prompt = 章节框架（模板真实章节）+ 要素 + 公司审定条款口径摘要。

```
你是企业合同起草专家。基于下方合同要素，按《{模板名}》的标准章节结构起草合同草稿。

## 合同要素
（按 elementsSchema 字段列出）

## 标准章节结构（必须完整保留以下章节与条款口径）
（从模板 docx 提取章节标题 + 关键条款口径摘要，如 ai-service 的：
  一、服务内容 1.1-1.2 / 二、结算条款 / 三、甲方权利义务 3.1-3.6 /
  四、乙方权利义务 / 5.1 知识产权 / 5.2 保密约定 / 六、违约责任 / 七、争议解决）

## 输出要求
1. 按模板章节结构输出完整合同，Markdown 格式（## 章节标题 + 条款序号）
2. 要素嵌入对应条款，缺省信息用【待补充】标注
3. 公司审定条款口径（知识产权归属、保密责任、责任限制等）原样保留
4. 文末注明"本稿由 AI 生成，仅供参考，需经法务审阅后生效"
```

> 模板全文（143 行，约 3-5k tokens）可作为参考上下文注入 prompt，确保口径准确；MVP 用章节框架 + 关键条款摘要（prompt 体积可控）。

### 5. 前端 markdown-to-docx 样式参数化

改造 `web/src/utils/markdown-to-docx.ts`：

```typescript
export type ContractDocStyle = {
  pageMargin?: { top: number; right: number; bottom: number; left: number }
  body?: { fontEastAsia: string; fontAscii: string; sizePt: number; lineSpacing?: number }
  title?: { fontEastAsia: string; fontAscii: string; sizePt: number; bold?: boolean; align?: 'center' | 'left' }
  heading?: { sizePt: number; bold?: boolean }
}

// 新签名：接收可选样式，缺省用默认（保持向后兼容）
export async function markdownToDocxBlob(
  content: string,
  filename: string,
  style?: ContractDocStyle,
): Promise<Blob>
```

**docx 库中文字体关键**：docx 库 `IRunOptions.font` 支持 `eastAsia`/`ascii`/`hAnsi`——`font: { eastAsia: '楷体', ascii: 'Arial' }` 保证中文楷体、西文 Arial（当前实现若只设 name 需补 eastAsia）。

**DownloadMenu 扩展**：新增可选 prop `:docx-style="style"`，透传给 markdownToDocxBlob；缺省行为不变。

**ContractView 集成**：模板详情带 style + elementsSchema（GET /contract-templates 返回），下载时传模板 style。

### 7. 实施步骤

1. **解析模板**：脚本（node + mammoth + 简单 XML 解析）从 3 个 docx 提取：样式参数（docDefaults + 标题段落 + pgMar）→ style JSON；章节结构 → prompt；要素字段 → elementsSchema JSON
2. **转换 .doc**：2 个 `.doc`（保密 V4.5、技术开发）人工用 WPS/Word 转 `.docx` 后入库（一次性）
3. 复制 3 个模板源文件到 `api/storage/contract-templates/{slug}/`
4. Prisma：ContractTemplate 加 style/elementsSchema/sourceFile → migrate
5. seed：3 个新模板（完整 prompt + 样式 + 要素 schema），旧 3 个 isActive=false
6. 前端 `markdown-to-docx.ts` 样式参数化（eastAsia 中文字体）
7. 前端 `DownloadMenu` 加 docx-style prop
8. 前端 `ContractView` 按 elementsSchema 动态渲染表单（替代硬编码 5 字段）+ 下载传模板样式
9. 验证：导出 docx 与模板对比（字体/字号/页边距）；业务端生成→下载→WPS 打开检查
