## Problem Statement

华北IU销售包正和与法务BP彭宇欣之间的合同处理目前走 CRM 流程：包正和在 CRM 提交合同申请 → 彭宇欣下载合同、人工审查、回传意见。痛点：合同协作是**法务最高频的工作**，但缺乏 AI 辅助起草与审查、无法在线协作、版本流转靠邮件/即时通讯来回传文件。

合同协作是 PRD 核心流程 2（F-CONTRACT-01~09），完成它之后，v0.0.1 MVP 的两大业务闭环（业务咨询 + 合同协作）全部打通。

## Demand Evidence

- **包正和**（华北IU销售）："客户要求改合同条款，我先找模板自己改一版，再发给法务审——来回要 1~2 天，能不能让 AI 先按模板生成一版，我改重点，法务只审关键条款"
- **彭宇欣**（法务BP）："80% 的合同风险是重复的（责任上限、违约金比例、知识产权归属），AI 先标出来，我只复核和补特殊条款"
- 现有工单模块已预留 `kind=contract` 类型和 `ContractTemplate` 设计空间，业务咨询闭环已跑通，合同协作是同一架构的自然延伸

## Status Quo

当前流程：业务人员下载/找模板 → 本地 Word 编辑 → 发钉钉/邮件给法务 → 法务审查 → 反馈修改意见 → 业务再改 → 再回传。全链路依赖即时通讯，无留痕、无追踪、无 AI 辅助。一次合同审阅通常 2-3 轮往返，每轮 0.5~1 天。

## Target User & Narrowest Wedge

**第一手用户**：包正和（业务端发起，AI 生成草稿）→ 彭宇欣（法务端审查定稿）→ 包正和（收到定稿）

**最窄可用版本**（MVP 闭环）：
1. 包正和在业务端选择合同模板（渠道合作/技术服务/保密协议）→ 填写要素（对方主体/金额/期限/主要条款）
2. AI 基于模板 + 要素生成合同草稿，SSE 流式渲染，支持 .docx 下载
3. 包正和本地编辑草稿后**上传修订版**（文件真正落盘到服务器）
4. 包正和点击"发起法务审阅"→ 创建 contract 工单 → 法务端收到
5. 彭宇欣在法务端看到 AI 风险审查 + 附件可下载 → 修改定稿 → 回传
6. 包正和在"我的记录"看到定稿并下载

## Constraints

- **复用而非重建**：数据模型复用 Project（kind=contract）+ ProjectMessage + ProjectEvent，与业务咨询一致
- **文件需要真实存储**：合同文件是协作交付物，需落盘服务器（区别于咨询模块"客户端读文件拼 prompt"）
- AI 引擎统一通过 Codex CLI（`codex exec`），SSE 流式输出
- 技术栈不变：NestJS + Prisma + MySQL + Vue 3 + Apple 风格纯 CSS
- 条款差异比对（F-08）、合同模板管理（F-09）为 P1，v0.1.0 再做

## Premises（已确认 2026-08-03）

1. ✅ MVP 做完整闭环（模板选择 → AI 生成草稿 → 上传修订 → 发起审阅 → 法务 AI 审查 + 人工定稿 → 回传下载）；条款差异比对（F-08）、模板管理（F-09）后移 v0.1.0
2. ✅ 复用 Project 消息模型（kind=contract），不新建独立合同表
3. ✅ 新增本地文件存储：`ContractFile` 表 + 服务器磁盘目录（`api/storage/contracts/`），MVP 不引入 OSS/S3
4. ✅ 3 个内置模板以静态 prompt 形式提供（`ContractTemplate` 表 + 种子数据），不做模板库 UI

## Approaches Considered

### Approach A: 复用 Project + 最小新增 ✅
复用 Project（kind=contract）+ ContractTemplate 表 + 本地文件存储（ContractFile 表 + multer + 磁盘落盘）。
- Effort: L（人 ~2 天 / CC ~30min）
- Risk: Low-Med（唯一新增点是文件存储）
- Pros: 闭环完整；消息流/SSE/权限/下载全复用；ContractTemplate 表为 P1 模板管理留好扩展点
- Cons: 文件存储是新依赖（multer + 磁盘目录）
- Reuses: Project 消息模型、状态机、@Roles、ChatInputBar / DownloadMenu / MarkdownContent / useFileUpload
- Completeness: 9/10

### Approach B: 轻量版——仅 AI 生成草稿
只做模板 + 要素 → AI 生成草稿 → .docx 下载，无上传回传、无法务审阅工单。
- Effort: S（人 ~0.5 天 / CC ~10min）
- Risk: Low
- Pros: 交付最快
- Cons: 闭环不完整，无法务审阅环节，合同无法协作——不满足 PRD F-CONTRACT-04~07
- Completeness: 5/10

### Approach C: 独立 ContractModule + 版本表
独立 Contract / ContractVersion / ContractComment 表，条款级版本对比。
- Effort: XL（人 ~5 天 / CC ~1h）
- Risk: Med
- Pros: 功能最全（版本对比、条款级审阅）
- Cons: 与现有 Project 消息流重复，跨表查询维护成本高，MVP 过度设计
- Completeness: 10/10（但超出 MVP 范围）

## Recommended Approach

**Approach A**。合同协作与业务咨询共享同一套工单架构，额外建表带来的"我的记录"跨表查询和维护成本远大于混用 Project 表的代价。文件存储是合同场景不可绕过的差异点，用最小的磁盘落盘方案解决，为 v0.1.0 OSS 迁移预留接口。

## Design

### 1. 整体流程

```
业务端 /business/contract
        │
        ▼
  选择合同模板（渠道合作/技术服务/保密协议）
        │
        ▼
  填写关键要素（对方主体/金额/期限/主要条款）
        │
        ▼
  POST /api/contracts/generate ──→ 创建 Project(kind=contract, route=llm)
        │                              │
        ▼                              ▼
  AI 生成合同草稿（SSE 流式）      [user] 要素输入
        │                        [event] 系统创建合同草稿
        ▼
  [assistant] 草稿全文（Markdown）
        │
        ├── 下载 .docx（DownloadMenu）
        │
        ├── 上传修订版（本地编辑后回传）→ ContractFile 落盘
        │
        └── 发起法务审阅 → route=legalbp, status=待复核
                 │
                 ▼
        法务端收到 contract 工单
                 │
                 ▼
        AI 风险审查（contract 审查 prompt）→ [assistant] 风险清单
                 │
                 ▼
        法务 BP 复核定稿 → [legal] 定稿意见 → 回传
                 │
                 ▼
        status=已回传 → 业务端"我的记录"可见 → 定稿下载
```

### 2. 数据模型（Prisma，新增）

在现有 schema 基础上新增两张表：

```prisma
// 合同模板（3 个内置模板种子数据；P1 模板管理直接复用此表）
model ContractTemplate {
  id          String   @id @default(uuid())
  slug        String   @unique @db.VarChar(64)  // channel-cooperation | tech-service | nda
  name        String   @db.VarChar(128)         // 渠道合作协议 | 技术服务合同 | 保密协议
  category    String   @db.VarChar(32)          // 渠道合作 | 技术服务 | 保密
  description String?  @db.VarChar(512)         // 适用场景说明
  prompt      String   @db.Text                 // 生成 prompt 模板（含要素占位符）
  isActive    Boolean  @default(true) @map("is_active")
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  @@map("contract_templates")
}

// 合同附件（本地磁盘文件，DB 只存元数据）
// revised/final 由平台上传接口产生；source/attachment/main_contract 仅供 CRM A1 入站原文件使用。
model ContractFile {
  id           String   @id @default(uuid())
  project      Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  projectId    String   @map("project_id")
  kind         ContractFileKind
  originalName String   @map("original_name") @db.VarChar(256)
  storedName   String   @map("stored_name") @db.VarChar(256)  // uuid.ext，磁盘文件名
  mimeType     String?  @map("mime_type") @db.VarChar(128)
  size         Int
  uploadedBy   String   @map("uploaded_by")                  // FK → users.id（拿显示名，工程评审决策 #9）
  uploader     User     @relation(fields: [uploadedBy], references: [id])
  createdAt    DateTime @default(now()) @map("created_at")

  @@index([projectId])
  @@map("contract_files")
}

enum ContractFileKind {
  source
  attachment
  main_contract
  revised
  final
}
```

**Project 模型新增字段**（在现有 model 上追加）：

```prisma
  // 合同模板溯源（工程评审决策 #9）
  contractTemplateSlug String? @map("contract_template_slug") @db.VarChar(64)
  files                ContractFile[]
```

**User 模型新增反向关系**：

```prisma
  contractFiles ContractFile[]
```

**磁盘存储约定**：
```
${CONTRACT_STORAGE_DIR}/{projectId}/{storedName} # storedName = uuid.ext
${CONTRACT_STORAGE_DIR}/.staging/...             # 校验成功后原子移动；失败清理
api/.gitignore → 忽略 storage/ 目录
```

目录权限固定为 `0700`，文件固定为 `0600`。单实例可使用本地持久盘；多实例 API/Worker 必须将
`CONTRACT_STORAGE_DIR` 挂载到同一共享持久卷并纳入备份。数据量增大后迁移 OSS/S3 时，仅替换
ContractFileService 的读/写实现，DB 元数据结构不变。

### 3. API 设计（NestJS ContractModule）

```
# 合同模板（P1 模板管理的基础）
GET    /api/contract-templates              # 可用模板列表（Roles: business, legal_bp, legal_lead）
       Response: [{ slug, name, category, description }]

# 生成合同草稿（核心入口）
POST   /api/contracts/generate              # Roles: business, legal_bp, legal_lead
  Body: {
    templateSlug: string,                    # 必填，对应 ContractTemplate.slug
    elements: {
      partyA?: string,                       # 我方主体（默认当前用户公司）
      partyB?: string,                       # 对方主体
      amount?: string,                       # 金额
      term?: string,                         # 期限
      clauses?: string,                      # 主要条款/特殊要求
    },
    projectId?: string                       # 可选：已有合同工单内继续生成（追加消息）
  }
  Logic:
    1. 查 ContractTemplate（slug）→ 组装合同起草 prompt（模板 prompt + 要素 + 任务）
    2. 无 projectId: **ContractService 直接 prisma 建工单**（kind=contract, route=llm,
       risk=P2 固定, status=分析中, title="合同草稿·{template.name}", creatorId,
       contractTemplateSlug=slug）
       → 插入 user 消息（要素摘要）+ event("AI 正在生成合同草稿…")
       —— ⚠️ 必须绕过 ProjectService.create()：其内部写死 riskService.assess + 咨询四段式
           prompt（buildConsultPrompt），不可为合同复用（工程评审决策 #2）
    3. 有 projectId: 校验归属（creatorId=currentUser）且 route=llm 未升级 → 追加 user 消息
       （守卫防把已升级工单打回）
    4. 调 CodexService.executeStream(合同 prompt, { timeout: 300_000 }) → SSE 流式推草稿
       （合同草稿远长于咨询回复，timeout 放宽到 300s，见工程评审决策 #7）
    5. 流结束: 插入 assistant 消息（草稿全文）→ status=待复核（表示"待下一步：下载/上传/发起审阅"）
    6. SSE final: { projectId, status: "待复核" }
  Response: SSE 流

# 业务端发起法务审阅（新增，工程评审决策 #3）
POST   /api/contracts/:id/submit-review      # Roles: business
  Body: {}
  Logic:
    1. 校验 project.kind=contract && creatorId=currentUser
    2. 原子更新 WHERE route=llm 守卫 → data { route: legalbp, status: 待复核 }（防重复提交）
    3. event("已发起法务审阅，通知法务BP") + DingTalkAdapter 通知
  Response: { projectId, status: "待复核" }

# 法务端 AI 风险审查（新增，工程评审决策 #4）
POST   /api/contracts/:id/review            # Roles: legal_bp, legal_lead
  Body: {}
  Logic:
    1. 校验 project.kind=contract && status=待复核
    2. 取最新合同文本：优先最新 ContractFile(revised) 的 mammoth 抽取文本，
       否则最新 assistant 草稿消息
    3. 调 CodexService(合同审查 prompt) → SSE 或一次性 assistant 消息（风险清单）
  Response: SSE 流 / { done: true }

# 附件（业务端上传修订版 / 法务上传定稿，双方下载）
POST   /api/projects/:id/files              # Roles: business, legal_bp, legal_lead
  multipart/form-data: { file: Binary, kind: "revised" | "final" }
  Logic:
    1. **权限校验**（工程评审决策 #5）：business 仅 creatorId=currentUser；
       legal 仅 ownerId/legalBpId=currentUser 或工单未分配
    2. multer diskStorage 写入 staging → 校验扩展名白名单(.docx/.pdf/.txt/.md)、文件头和大小(≤20MB)
       —— 不信任客户端 mimetype，见工程评审决策 #6
    3. DOCX/PDF/TXT/MD 均必须抽取出非空可审查正文；伪造扩展名、损坏/加密 DOCX、扫描 PDF、
       非 UTF-8 文本统一返回 422 `FILE_VALIDATION_FAILED`，不得落入正式目录或数据库
    4. 校验通过后移动到 `${CONTRACT_STORAGE_DIR}/{projectId}/{uuid.ext}`；目录 0700、文件 0600
    5. 在同一事务中写入 ContractFile、对应 revised/final ContractDocument 和正文消息；失败删除正式文件
    6. createEvent("上传了合同文件：{originalName}")   # 法务端时间线可见
  Response: { fileId, originalName, size, kind, textExtracted: true, extractedChars }

GET    /api/projects/:id/files              # Roles: business, legal_bp, legal_lead
       → 附件列表（含上传人显示名 + 时间，uploadedBy include user）

GET    /api/projects/:id/files/:fileId      # 下载（读磁盘流，Content-Disposition 用
       RFC5987 filename*=UTF-8'' 支持中文名）

# 复用现有 ProjectModule（小改 1 处）
POST   /api/projects/:id/messages           # 追问/补充（SSE）
POST   /api/projects/:id/reply              # 法务回传定稿（status=待复核 → 已回传）
POST   /api/projects/:id/cancel             # 取消
GET    /api/projects/mine                   # 业务端"我的记录"（contract 类型自动出现）
GET    /api/projects/:id                    # 详情（含附件 files 预加载）
       # findAll 分组：route=llm 的 contract 工单改为进"合同协作"分组（工程评审决策 #8）
```

**权限矩阵**（service 层 ownership 校验，工程评审决策 #1）：

| 操作 | business | legal_bp/lead |
|------|:---:|:---:|
| 选模板 + 生成草稿 | ● | ● |
| 上传修订版 | ●（仅自己创建的工单） | ●（仅自己处理/未分配） |
| 下载附件 | ●（仅自己创建的工单） | ●（仅自己处理/未分配） |
| 发起法务审阅 | ●（仅自己创建的工单） | — |
| AI 风险审查 | — | ●（仅自己处理/未分配） |
| 定稿回传 reply | — | ● |

### 5. 合同生成 Prompt 模板

**模板 Prompt 结构**（ContractTemplate.prompt 存 3 份，每份含章节框架 + 条款指引）：

```markdown
你是企业合同起草专家。基于下方合同要素，起草一份《{模板名称}》草稿。

## 合同要素
- 我方主体（甲方）：{partyA}
- 对方主体（乙方）：{partyB}
- 合同金额：{amount}
- 合同期限：{term}
- 主要条款/特殊要求：{clauses}

## 模板章节框架
（渠道合作协议：合作模式 / 授权与排他 / 结算与分成 / 业绩考核 / 保密与竞业 / 违约责任 / 争议解决）
（技术服务合同：服务范围 / 交付物与验收 / 付款节点 / 知识产权归属 / 保密 / 维保服务 / 违约责任）
（保密协议：保密范围 / 保密期限 / 例外情形 / 违约责任 / 争议解决）

## 输出要求
1. 输出完整合同条款，使用 Markdown 格式（标题 ## + 条款序号）
2. 金额、期限等要素直接嵌入对应条款，缺省信息用【待补充】标注
3. 对不合理的要素（如明显违反法律法规的条款）在文末"⚠️ 风险提示"中说明
4. 文末注明"本稿由 AI 生成，仅供参考，需经法务审阅后生效"
```

**法务端 AI 风险审查 Prompt**：

```markdown
你是企业合同审查专家。审查下方合同内容，逐条识别法律风险。

## 输出格式（每条风险独立成块）
### 第 N 条 · {条款标题}
- 原文摘要：…
- 风险等级：【高/中/低】
- 风险分析：…
- 修改建议：…

## 审查要点
- 违约责任、责任上限、违约金比例是否失衡
- 知识产权归属与许可范围
- 保密条款、竞业限制的合理性与可执行性
- 付款节点与交付验收的对应关系
- 争议解决条款（管辖法院/仲裁）的合法性
- 是否有明显违反强制性法律法规的条款

## 结尾
输出"总体评价"：该合同整体风险等级（高/中/低）+ 必须修改的核心条款清单
```

### 8. 状态机（复用现有 Project 状态机，语义修正见工程评审决策 #8）

```
生成草稿(kind=contract, route=llm, status=分析中 → 待复核)
  → 业务端可选：下载草稿 / 上传修订版（status 保持 待复核）
  → 业务端"发起法务审阅"(submit-review) → route=legalbp, status=待复核（原子守卫 WHERE route=llm）
      → 法务 AI 风险审查(review) → 人工定稿 reply() → status=已回传
      → 法务拒绝/异常 → status=待处理（复用 isFailed 异常路径）
  → 业务端撤回 → status=已取消
```

**状态语义**：`已回传` 仅表示"法务已定稿"，消除"草稿已出"与"法务定稿"的混淆。草稿生成完成 = `待复核`（等待下一步操作），不是已回传。`reply()` 复用现有原子化更新（WHERE status=待复核 守卫防竞态）。

**findAll 分组修复**：现有 [project.service.ts:143](LegalPlatform/api/src/modules/project/project.service.ts#L143) `if (p.route === 'llm') groups['数字分身处理']` 会把 route=llm 的 contract 草稿分到错误分组。改为**先按 kind 判断**：`kind === 'contract'` 一律进"合同协作"分组（无论 route），再按 route/status 处理其余。
