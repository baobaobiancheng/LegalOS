## Problem Statement

华北IU销售包正和与法务BP彭宇欣之间的法务协同目前走CRM流程，但CRM缺少三个关键能力：**钉钉自动拉群实时协作**、**AI原生驱动的初稿生成与审阅**、**工单周报自动汇总**。工单模块是平台的核心骨架，需要打通"业务发起→AI初稿→法务复核→回传"的完整闭环。

## Demand Evidence

- **包正和**（华北IU销售）：在CRM发起合同申请是已知流程，需要更快地获得AI生成的初版法务意见
- **彭宇欣**（法务BP）：同时处理多个工单，需要AI生成初稿、自己只做review，钉钉拉群减少来回沟通
- 平台上线后包正和和彭宇欣是第一手使用者

## Status Quo

CRM里发起合同流程 → 法务在CRM里回传意见。流程慢，无AI辅助，无自动拉群，无周报生成。

## Target User & Narrowest Wedge

**用户**：包正和（业务端发起）→ 彭宇欣（法务端处理）→ 包正和（收到回传结果）

**最窄可用版本**：一个工单从创建到回传的完整闭环——包正和在业务端点击"发起咨询"→ 系统自动风险判定 → P2由LLM直答 / P1+P0创建工单+钉钉模拟通知 → 彭宇欣在法务端看到AI生成的初稿 → 修改后点击"回传" → 包正和看到结果。

## Constraints

- 钉钉API和CRM API目前都没有，需用Adapter模式+模拟数据占位
- 周报功能不在本次MVP（PRD 4.9，后续Phase），但工单结构设计需预留周报所需字段
- AI引擎统一通过Codex CLI调用（`codex exec`）
- 技术栈：NestJS + Prisma + MySQL + Vue 3 + Apple风格纯CSS

## Premises

1. ✅ 完整链路：业务发起 → AI初稿 → 法务复核 → 回传（MVP目标）
2. ✅ 外部集成采用Adapter模式+模拟数据，后续替换真实实现
3. ✅ 周报先不做，优先工单闭环

## Approaches Considered

### Approach A: 全功能一步到位 ✅
工单CRUD + 消息流 + 状态机 + Codex CLI集成 + 钉钉/CRM Adapter占位。后端ProjectModule + MessageModule，前端工单列表页 + 对话页。
- Effort: L (3天/人 ~ 1h/CC)
- Risk: Low
- Pros: 一个模块打通所有后续开发的基础；Adapter模式保证后续替换成本为零
- Cons: 代码量大，但CC+AI不需考虑这个
- Completeness: 9/10

## Recommended Approach

**Approach A**。工单模块是整个平台的骨架——后续业务咨询、合同协作、法规检索都依赖它。一次做完比分开做效率更高，Adapter模式天然隔离未就绪的外部依赖。

## Design

### 1. 数据模型（Prisma，新增）

```prisma
model Project {
  id            String   @id @default(uuid())
  kind          ProjectKind     // consult | contract | research | draft
  title         String
  status        ProjectStatus   @default(分析中)
  risk          RiskLevel       @default(P2)
  route         String          @default("legalbp")  // llm | legalbp
  skillId       String?         // 技能库ID，当前为null（技能库后续实现）
  skillName     String?
  ownerId       String          // 当前处理人
  legalBpId     String?         // 指定法务BP
  creatorId     String          // 创建者（业务人员）
  requesterName String?         // 提出人姓名
  requesterDepartment String?   // 提出人部门

  // CRM 上下文（Adapter 占位）
  crmReference  String?         // CRM单据编号
  crmCustomer   String?         // 客户名称
  crmOpportunity String?        // 商机编号

  // 钉钉（Adapter 占位）
  dingtalkChatId String?        // 钉钉群ID
  dingtalkMembers String?       // 群成员JSON数组

  // AI 相关
  model         String?         // 使用的模型
  deliveryMode  String?         // model | local-rule
  result        String?         @db.Text  // 最终结果

  // 周报预留
  weeklyReportLabel String?     // 周报归类标签

  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  messages      ProjectMessage[]
  events        ProjectEvent[]
  creator       User @relation("CreatedProjects", fields: [creatorId], references: [id])
  owner         User @relation("OwnedProjects", fields: [ownerId], references: [id])
  legalBp       User? @relation("LegalBpProjects", fields: [legalBpId], references: [id])

  @@map("projects")
}

model ProjectMessage {
  id        String   @id @default(uuid())
  project   Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  projectId String
  role      String   // inbound | user | assistant | legal | event
  text      String   @db.Text
  label     String?
  createdAt DateTime @default(now())

  @@map("project_messages")
}

model ProjectEvent {
  id        String   @id @default(uuid())
  project   Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  projectId String
  text      String   // "14:32 · 工单已创建并通知法务BP"
  createdAt DateTime @default(now())

  @@map("project_events")
}
```

### 2. API 设计（NestJS ProjectModule）

```
POST   /api/projects                    # 创建工单 + 触发钉钉通知(Adapter)
GET    /api/projects                    # 列表 (?status=&kind=&page=&size=)
GET    /api/projects/:id                # 详情（含消息和事件）
PATCH  /api/projects/:id                # 更新（状态/转派/风险/回传）
POST   /api/projects/:id/messages       # 发送消息 → body: { text, role }
                                       #   → P2+llm路由: 调用 CodexService → SSE 流式返回AI答复
                                       #   → P1/P0+legalbp路由: 只存消息，等待人工
POST   /api/projects/:id/reply          # 法务BP正式回传 → 状态→已回传 + 触发CRM回写(Adapter)
POST   /api/projects/:id/cancel         # 取消工单
POST   /api/projects/:id/transfer       # 转派给另一个法务BP

# Adapter 接口（内部调用，非前端直接访问）
GET    /api/projects/:id/crm-context    # 获取CRM上下文（Mock实现）
POST   /api/projects/:id/dingtalk-notify # 发送钉钉通知（Mock实现）
```

### 4. 风险判定服务（可复用）

```typescript
// src/modules/project/risk.service.ts
const P0_KEYWORDS = ['刑事责任', '监管调查', '紧急禁令', '重大安全事故']
const P1_KEYWORDS = ['无限责任', '数据出境', '跨境', '个人信息', '诉讼', '监管', '并购', '股权', '竞业']

function assessRisk(query: string): { risk: RiskLevel; route: ProjectRoute } {
  if (P0_KEYWORDS.some(k => query.includes(k))) return { risk: 'P0', route: 'legalbp' }
  if (P1_KEYWORDS.some(k => query.includes(k))) return { risk: 'P1', route: 'legalbp' }
  return { risk: 'P2', route: 'llm' }
}
```

### 6. 状态机（关键流转）

```
创建(create)
  → 分析中(analyzing): AI正在生成初稿
    → 待复核(review): AI初稿已生成, 等待法务BP复核
      → 已回传(resolved): 法务BP点击回传 → 钉钉通知 + CRM回写
      → 待复核(循环): 法务BP继续修改
    → 待处理(pending): LLM调用失败，转人工
  → 已取消(cancelled): 业务撤回
```

### 7. 消息流（一次完整对话示例）

```
[inbound]  来自 Business OS · 演示适配器          # 系统消息
[user]     客户要求把责任上限从1倍改成2倍…          # 包正和
[event]    系统自动判定 P1 风险，创建工单            # 状态事件
[event]    钉钉群已创建（模拟），已通知彭宇欣         # 钉钉事件
[event]    AI 正在生成初稿…                        # 处理状态
[assistant] 核心结论：不建议接受两倍责任上限…        # AI草稿
[legal]    已核实AI分析，补充了…同意回传             # 彭宇欣正式回复
[event]    已回传业务端，包正和可见                  # 回传事件
```

## Engineering Review Decisions（/plan-eng-review, 2026-07-31）

| # | 决策 | 影响 |

| 1 | 状态机分离正常/异常路径：`isFailed` 布尔字段，正常流转 analyzing→review→resolved，异常时 isFailed=true → pending | Prisma schema 加字段 |
