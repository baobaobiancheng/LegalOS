## Problem Statement

LegalOS(法务AI平台)当前用自建账号密码登录(admin/legal_bp/business 种子账号 + JWT),用户身份与公司统一身份(CAS)完全脱节。要求**全部登录改为公司 CAS 账号登录**,实现平台账号 ↔ 公司身份的统一定位——与 CRM 对接文档「人员映射统一公司 CAS 账号」决策呼应,是公司身份体系的收口。

## Demand Evidence(背景依据)

- 公司级强制:全公司系统走 CAS 统一认证;CRM 已是 CAS 账号。
- CRM 对接文档已定:「人员映射统一用公司 CAS 账号」,CRM 需提供 CAS 登录实现方式。
- 用户明确指令:「我当前的登陆都要修改为cas账号登陆」。

## Status Quo(现状)

- LegalOS:username/password + JWT(accessToken/refreshToken);`POST /auth/login` / `refresh` / `me` / `logout`。
- `User` 表:`username @unique`、`passwordHash`(**非空**)、`role`(Role 枚举)、`dingtalkUserId @unique`(钉钉绑定先例可复用);种子账号 FK:法律/业务域映射表、技能/模板的 `creatorId` 指向 admin/legal_bp/business。
- 测试/CI:147 API 单测 / 20 web 测试 / E2E(`login.smoke.spec.ts` 断言密码输入框 + 种子账号页脚)全依赖密码登录。
- 用户:法务/业务人员需记忆一套与公司身份无关的 LegalOS 独立账号。

## Target User & Narrowest Wedge

- 用户:公司员工(法务 BP、业务人员),用公司 CAS 账号(如 `zhenghe.bao`)登录 LegalOS。
- Wedge:预发环境 CAS 登录打通——员工从 CAS 门户点入口或前端跳 CAS,`ticket→validate→自动建号→JWT`,完成一次真实登录。

## Constraints

- **NestJS 无 Java starter**:`cas-spring-boot-starter` 是 Java/Spring,须按 HTTP 协议在 NestJS 自实现。
- **ticket 安全**:32位UUID、5分钟、一次性;HTTPS;日志禁打明文 ticket。
- **projectCode 是钥匙**:CAS 后台注册 LegalOS 项目 code + 认证登录URL + 角色(注册角色仅为满足 CAS 项目配置/门禁——用户须开通项目+角色才拿得到 ticket;LegalOS **不信任 roleCode** 做领域判断)。
- **领域角色平台自管(P2)**:不信任 CAS `roleCode` 当领域角色。
- **测试旁路(P5)**:dev/CI 不能依赖真 CAS。

## Premises

1. **P1 身份替换**:CAS 是唯一身份来源,生产/预发移除密码登录;dev/CI 保留密码旁路。
2. **P2 领域角色平台自管 + 管理员引导**:CAS 认证身份 + 项目门禁;领域角色按 casUsername 平台内维护;**一期必须有 admin 来源**(见方案 A)。
3. **P3 projectCode 钥匙**:CAS 后台注册项目;所有 validate/open API 以它为准。
4. **P4 账号供给=自动建号(upsert)**:首次登录 `upsert` 建 User。
5. **P5 测试旁路**:dev/CI 用**现有密码登录**作旁路(已存在,测试零改动);本地 CAS 流程调试用 `CAS_BYPASS`(mock validate),**生产硬禁止**。
6. **P6 跨系统互调复用全域通行证**:后续 `CasToken` header + `/api/validateToken`(一期不做)。

## Approaches Considered

### Approach A: 最小落地(登录替换)—— 一期
- 核心:
  1. `User.casUsername @unique` + migration;`passwordHash` 保持非空,自动建号写入**随机不可用哈希**(不能密码登录)。
  2. NestJS `CasAdapter`(复用 DingTalkAdapter 模式):真实现调 `GET {CAS_HOST}/validate?ticket=..&service=..`(protocol 细节以 clone 的 starter 为准,mock 供测试)。
  3. `POST /auth/cas-login`:`ticket + service` → validate → **`upsert`**:
     `where:{ casUsername }` → `create:{ username:casUsername, displayName:name, passwordHash:随机, role: 是否CAS_ADMIN命中 ? ADMIN : 默认 }` + `update:{ displayName, role: 是否CAS_ADMIN命中 ? ADMIN : 不降级 }`(保证 admin 名单后期加入也能升级)→ 复用 `issueTokens` 发 JWT;写 `LoginAudit`(与现登录对齐)。
  4. **管理员引导(修 #1)**:配置 `CAS_ADMIN_USERNAMES`(env,如 `zhenghe.bao`)——命中时**创建或升级**为 `ADMIN`(upsert 的 create/update 都判定);保证生产有 admin 管成员/技能/模板。不做 CAS 角色映射,避免依赖 roleCode。
  5. 前端:登录页提供「使用公司账号登录」按钮 → 跳 CAS;回跳带 `?ticket=` → POST `/auth/cas-login`;token 存续。**dev 环境渲染 密码表单 + CAS 按钮 双入口**(密码旁路与 CAS 调试并存),生产/预发只渲染 CAS 按钮。
  6. **旁路(修 #5)**:dev/CI 保留现有密码登录(环境矩阵下);`CAS_BYPASS=true` 时 `POST /auth/cas-login` 走 mock validate(本地联调),**生产 `NODE_ENV==='production'` 强制拒绝启用**。
  7. **种子账号处置(修 #4)**:不删除 DB 行(避免 bpDomainMap/技能/模板 FK 断裂);仅生产/预发禁用密码登录入口——种子行无害留存,dev/CI 照常可用。
- Effort: M | Risk: 低 | Reuses: DingTalkAdapter 模式、issueTokens、LoginView、LoginAudit

### Approach B: 落地 + 账号治理
- A + 定时同步 CAS 项目用户列表(`projectUserList` open API)预建/回收账号;离职/停用自动降级(补 JWT 会话无登出的风险)。
- Effort: L | Risk: 中 | Reuses: A + MembersService 同步模式、Outbox

### Approach C: 完整集成(含跨系统通行证)
- B + 全域 API 通行证(`CasToken` header 调 CRM 等)+ CAS 管理员角色→ADMIN 映射。
- Effort: XL | Risk: 中高 | Reuses: B + CrmAdapter

## Recommended Approach

**Approach A(一期)**——登录替换 + 自动建号(upsert)+ admin 引导 + 双旁路(dev 密码 / CAS_BYPASS mock)+ 种子不删行。账号治理(B)与跨系统通行证(C)二期。

## 登录链路与 validate 协议(源码确认 2026-08-10,clone starter 核实)

```
【redirect 链路】
用户访问 LegalOS 登录页 → 点击「使用公司账号登录」
  → 跳 CAS(入口 URL 待确认:方式二 /api/cas/project/auth/{projectId} 或 CAS 门户)
  → CAS 校验项目权限后 302 回认证登录URL:https://legalos-pre.100credit.cn/login?ticket=xxx
  → 前端取 ticket → POST /auth/cas-login { ticket }   ← 不传 service(源码确认)
  → 后端 GET {CAS_HOST}/validate?ticket=xxx           ← 无 service 参数
  → 返回 CasAuthResult → upsert → JWT

【ticket 一次性】由 CAS 服务端消费;mock 测试要覆盖「二次使用被拒」路径。
```

**validate 协议(starter 源码确认,`cas-spring-boot-starter` `CasAuthService.validateTicket`)**:

- 请求:`GET {CAS_HOST}/validate?ticket={ticket}`(**无 service、无 projectCode 参数**)
- 响应 `CasAuthResult` JSON:
  `status`("success"=ok)/`msg`/`email`/`name`/`userId`/`username`/`proId`/`zone`/`zoneId`/`role`/`roleId`/`roleCode`/`deptId`/`deptName`/`vpnIp`/`projectCode`
- LegalOS 需要的字段:`username`(身份键)/`name`(displayName)/`email`/`deptName`(可选);`roleCode` 不信任(设计 P2)
- 配置仅两项必填:`host` + `projectCode`(projectCode 用于权限/角色查询类接口,validate 不传)
- **service 参数在本公司 CAS 不存在** —— 标准 CAS 的 service 契约不适用,设计已简化(T2 变为"无需 service")

## 工程审查锁定(plan-eng-review 2026-08-10,codex 外部审 28 条)

- **service 后端自供**:浏览器不传 service;前端跳 CAS 用后端下发的认证登录URL,后端 validate 用配置值(单一来源)。
- **存量迁移绑定**:数据迁移把种子用户 casUsername 绑真实 CAS 账号(admin→junfang.zhao / legal_bp→yuxin.peng / business→qiang.tian),防重复人。
- **角色预映射表**:CAS 账号→领域角色(钉钉 auto-bind 模式);未映射默认 business;`CAS_ADMIN_USERNAMES` 命中→ADMIN。
- **启动 fail-fast**:生产/预发缺 CAS 配置 / BYPASS / 密码登录未禁 → 拒绝启动;生产 `POST /auth/login` 403。
- **会话上限**:refresh 加 authMethod + 绝对过期;切换时吊销存量 password refresh。
- **isActive 已存在**(jwt.strategy.ts):cas-login 显式拒 inactive 用户。
- **validate 用 v2**(casToken 一期捕获,不落库防凭证风险)。
- **错误码**:ticket 无效→401;CAS 不可达→503(不重试,防消费一次性 ticket);BYPASS 误开→500。
- **hard gate**:clone cas-spring-boot-starter + 预发实测 validate 协议后再写 CasAdapter。
