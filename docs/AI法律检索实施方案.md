# AI 法律检索实施方案

> 状态：PROPOSED
>
> 范围：法务端独立检索页与咨询端 AI 搜法 / AI 类案
>
> 原则：优先复用已付费取得的权威证据，不复用过期结论；不把不完整的本地样本伪装成全库。

## 1. 产品决策

不向用户提供“是否先查已有数据集”开关。缓存是成本与性能策略，不是用户任务。

默认行为：

1. 先查本地的精确请求快照和权威文档库。
2. 缓存新鲜且覆盖当前请求时，直接返回，不调用供应商。
3. 缓存缺失、过期或证据不足时，才调用百鉴，成功后写回本地。
4. 界面显示“数据源与校验时间”，另提供显式的“刷新权威数据”操作。不做自动后台刷新，避免用户不知情的付费调用。

快捷检索与 AI 检索应保持两个清晰入口：

- **数据库检索**：关键词、筛选、分页、原文阅读，不经大模型改写。
- **AI 搜法 / AI 类案**：接受自然语言任务，Agent 拆解检索、读取原文、排序证据并生成可追溯报告。

## 2. 已验证的竞品模式

智合 AI 公开演示把「AI 搜法」分为法条定位、法规定位和法律问题；把「AI 类案」分为以案找案、案情分析和个性化制表。结果不是一张命中列表，而是持久化任务与可追问报告：

- AI 搜法输出总结、相关条文、现行/历史版本、发布机关、生效日期和全文入口。
- AI 类案先提炼锚点案件的核心法律问题，再给出裁判倾向、可比案例和案例内的「AI 摘要 / 本院认为 / 本院查明 / 裁判结果」。
- 产品同时保留案例法规数据库、高级筛选、历史、收藏、追问和报告导出。

北大法宝的公开产品也采用同样的分层：底层同时提供语义检索、关键词检索、精确法条、法条溯源和案例检索；上层生成可追溯结论或类案报告。

这意味着 LegalOS 不应把「单次关键词调用 + 列表」标记为 AI 搜法。

## 3. 付费调用复用架构

### 3.1 两层存储

**A. 权威文档库 `LegalSourceDocument`**

按 `source + externalId` 唯一存储从百鉴获得的法规或案例。保留：

- 类型、标题、机关/法院、文号/案号、日期、时效性和公开链接。
- 经标准化的正文或摘要、内容哈希、供应商工具版本。
- `fetchedAt` 、`lastVerifiedAt` 和 `verificationStatus`。

法规详情和案例原文可被不同查询交叉复用，这是最稳定的节费层。

**B. 精确请求快照 `LegalSearchSnapshot`**

对完整请求做规范化后的 SHA-256：

```text
hash(toolVersion + capability + normalizedQuery + filters + page + pageSize)
```

快照保留总命中数、页码、排序后的文档 ID/分数和到期时间。案情类自然语言可包含个人信息，缓存键仅保留哈希，不在新表内重复保存原始问题。

### 3.2 新鲜度

- 法规搜索快照：24 小时。
- 类案搜索快照：24 小时。
- 法规正文：按独立版本 ID 长期保留，30 天重新校验时效性与元数据。
- 裁判文书：长期保留，90 天校验元数据和公开链接。
- AI 报告不作为新问题的权威答案复用；只复用报告引用的证据。

刷新使用显式动作，不做 stale-while-revalidate 式的隐式付费。

### 3.3 并发与基础设施

一期不引入 Redis：

- MySQL/Prisma 保存文档和快照，唯一索引防止重复落库。
- 当前单 API 实例内用 `Map<requestHash, Promise>` 做 single-flight，同一请求只发起一次付费调用。
- 只有实际部署为多 API 实例，且监控证明重复调用造成可观成本时，再增加分布式锁。

## 4. 真正的 AI 搜法

### 4.1 任务类型

Agent 先将输入分为：

1. **法条定位**：已给出法规名与条号，直接精确查找并读取正文。
2. **法规定位**：已给出法规别名、文号或主题，检索并定位现行版本。
3. **法律问题**：从事实中抽取法律关系、争点和管辖范围，生成多组检索式。

### 4.2 Agent 工具链

当前 DSH 只向 Agent 开放了「法规关键词检索」，并且工具描述明确说不含条文正文，因此它不可能产生竞品那样的 AI 搜法结果。

目标工具链：

```text
意图识别
  -> 精确关键词检索 lawstar_data_professional_query
  -> 高级条件检索 lawstar_data_k_query（需要机关/区域/时效筛选时）
  -> 语义检索 lawstar_data_xl_query（自然语言问题）
  -> 候选去重与重排
  -> 对少量候选调用 lawstar_data_professional_detail
  -> 基于真实条文生成带引用报告
```

回答必须区分「条文原文」与「AI 分析」，引用只能指向工具返回的权威 ID。

## 5. 真正的 AI 类案

### 5.1 任务类型

1. **以案找案**：识别案号或已知裁判，将它作为锚点。
2. **案情分析**：抽取主体、请求权基础、核心事实、争点、程序阶段和希望结果。
3. **对比表/研究报告**：先固定比较字段，再检索与读取全文，禁止用搜索摘要猜测字段。

### 5.2 Agent 工具链

```text
拆解案情与法律问题
  -> 生成 2–4 组去识别化检索问题
  -> ldh_search 多轮召回
  -> 按相关度、法院层级、日期、案号完整性去重重排
  -> 对前 3–5 条调用 ldh_get_document
  -> 提取事实 / 争点 / 本院认为 / 裁判结果
  -> 输出裁判倾向、相似点、区别点和可采信程度
```

当前 LegalOS 只有 `ldh_search`，没有向 Agent 开放 `ldh_get_document`；所以现状只能做「相似案例摘要搜索」，不能对标竞品的深度类案分析。

LDH 当前可用筛选为国家、数据源、法院层级、管辖类型、地区和日期。智合演示中的案由、程序、文书类型、裁判结果等更细筛选，需要百鉴提供相应字段或增加中国案例数据源，不能靠前端伪造。

## 6. 分期实施

### PR-A：缓存与成本基线

- 新增权威文档、检索快照与快照明细表。
- 在 `BaijianMcpClientService` 上方增加 `LegalEvidenceRepository` 和 `CachedLegalResearchGateway`。
- 实现精确缓存、显式刷新、进程内 single-flight 与命中/成本指标。
- 界面显示「来自本地缓存 / 来自百鉴」与校验时间。

验收：同一请求在 TTL 内连续执行 10 次，只产生 1 次供应商调用；不同查询命中同一法规详情时不再请求正文。

### PR-B：AI 搜法报告

- 向 DSH 开放精确、高级、语义和法规详情工具，工具全部经过缓存网关。
- 新增意图类型、候选去重/重排、条文引用校验和证据充足性门控。
- 结果页使用持久化报告：总结、相关条文、关联法规、版本/时效提示、来源与追问。

验收：法条定位必须引用具体条文原文；法律问题必须至少使用一条已读取正文的权威来源；零结果时不冒充已检索结论。

### PR-C：AI 类案报告

- 实现 `ldh_get_document` 的类型化适配与长文限制，向 DSH 开放案例详情工具。
- 增加锚点案识别、多轮召回、候选去重、全文读取预算与案例对比 schema。
- 结果支持裁判倾向、相似/区别点、结构化对比表、原始来源和追问。

验收：每个可核验的案件事实必须来自 `ldh_get_document`；只有搜索摘要的案例必须降级标记；不得生成工具未返回的案号和裁判结果。

## 7. 必要指标

- `supplier_calls_total{tool}`
- `research_cache_hit_total{capability}`
- `research_cache_miss_total{reason}`
- `research_cache_saved_calls_total{tool}`
- `research_detail_reuse_total{source}`
- `research_supplier_cost_estimate`
- `research_evidence_verified_ratio`
- `research_zero_result_ratio`
- `research_latency_ms{stage}`

只有在指标证明精确缓存的收益已触顶，并且本地累积证据已有足够覆盖率时，才进入知识库/向量检索阶段。
