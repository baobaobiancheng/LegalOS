# LegalOS 全仓安全、健壮性与可维护性审查

## 范围与方法

- 审查基线：`97d3a3e`，`main`；开始时工作区无未提交变更。
- 范围：LegalOS API、Web、Prisma schema/迁移、部署脚本与直接/传递依赖，包含嵌入式 DSH 与百鉴调用链。基线 `api/src` 121 个跟踪文件，`web/src` 50 个跟踪文件（含测试、样式和资源）。
- 方法：全仓风险模式扫描，认证与对象权限、用户输入到数据库/文件/外部服务的调用链复核，异步终态与并发条件检查，现有测试与独立 MySQL 验证。不是仅审查最后一个提交。
- 不包括：邻接的独立 DSH 源码副本、第三方包逐行源码审计、真实 CAS/钉钉/CRM/模型供应商的渗透测试。源代码审查与依赖审计不能证明不存在所有漏洞。
- 审查与修改分阶段进行：首轮只读审查；修复后冻结代码，由主审复查最终 diff 和相关调用链。

### 可维护性评估

对基线 160 个非测试 TS/Vue 源文件进行 TypeScript AST 统计（Vue 仅统计 script）：83 个函数/方法/箭头回调超过 50 行，166 处显式 `any`。这不是 83 个独立缺陷，也不以行数为理由进行无验证拆分。

主要复杂点是 `ConsultationReplyOrchestrator.reply`（297 行）、`DshBaijianToolsService.createDefinitions`（237 行）、`ContractService.generateDraft`（227 行）、`ConsultationChatService.stream`（190 行）和业务咨询 `handleSend`（188 行）。这些位置需要围绕权限、运行所有权、事务边界和异常收尾分离职责，而非只做文件搬家。本次优先修复已发现的跨路径不一致，并抽取可复用的安全边界与 BP 匹配逻辑。

命名、注释与常量未仅凭风格列为阻断项；“压缩文件大小即 zip bomb 防护”“CAS ticket 已脱敏”等与实现不符的安全注释随对应修复同步纠正。

### 减少不必要的防御性编程

外部输入、认证授权、文件与网络 I/O、数据库竞争属于真实失败边界，保留校验、限额与明确错误语义。进入已验证的内部流程后，以明确类型和业务不变量为依据，避免重复判空、重复校验、宽泛 `catch` 后返回伪成功，以及用默认值掩盖缺失的必要依赖。

复审同时检查：成功路径是否清楚；异常是否由合适的一层处理；共享策略是否只有一个实现；新增抽象是否解决多个真实调用点的问题。不会单纯为了减少分支而移除权限、资源上限或事务一致性保证，也不以增加通用框架替代可读性改进。

具体调整：文件上传由一个 `finally` 负责 staging 清理；Worker 响应用判别联合类型表达成功与失败，取消无意义的计数兜底和未使用字段；共享法务处理人查询只选取实际需要的字段；运行 ID 改为必填，删除内部空 ID 分支；合同与咨询共用项目版本匹配规则，失败收尾统一到明确的调用点；错误日志输出受限诊断标签，不以宽泛异常消息充当业务响应。外部认证、文件限额和并发提交检查仍保留。

### 发布验证追加发现

- 当前 Prisma 6.19.3 的 `format` 命令不支持 CI 中使用的 `--check` 参数，需采用兼容的格式比对方式。
- 原 CI 运行 API 单元测试，但没有 Web 单元测试任务，无法替代本地 Web 测试门禁。
- 中间版本真实 HTTP 回归发现 multipart 的 `parts` 边界误拒正常“kind + file”上传；须按 Busboy/Multer 的实际事件语义设置解析上限，同时保留文件数与字段数限制。
- 真实有效 DOCX 上传暴露原有解析缺陷：JSZip 的 `nodeStream()` 不支持异步迭代，类型强转不改变运行时行为，导致有效文档被误报为损坏。须进行真正的流适配，继续执行展开体积限制，并覆盖有效 DOCX，而不仅测试损坏文件。

### 主审复审追加项

- S09 第一版修复仅排除已取消/转人工路由，未覆盖保留 LLM 路由的人工正式回复；项目版本与运行所有权必须同时参与结果提交，失效运行不能继续改变项目。
- S08 的批次新旧判断还需覆盖相同毫秒启动，不能依赖测试中的延时获得不同时间戳；数据库锁不能因测试替身缺少方法而被静默跳过。
- 未认领列表投影去除敏感字段后仍需保留分组所依赖的非敏感字段，保证 `items`、`groups` 与 `groupCounts` 语义一致。
- 依赖审计同时覆盖生产与开发工具；Web 生产依赖无公告不代表测试工具无风险。Web Vitest 2.x 的已知公告需要升级验证，不能跳过 CI 的高危门禁。
- 依赖覆盖应限定受影响版本链，不能为了修复 Express 4 的解析器而把 Express 5 的解析器降级到旧主版本。

## 发布注意事项

- 现有服务器历史输出确认进程名为 `legalos-api`、`legalos-web`，API 通过 `npm run start:prod` 启动；Web 历史输出为 Vite dev server。这不是当前服务器实时状态检查。
- 本次不启用 CRM，也不提供虚构的 CRM B1 接收地址。真实 CRM、CAS、钉钉与模型服务的端到端联调须独立验证。
- 不在常规升级中执行 `prisma db seed`，不对依赖使用 `npm audit fix --force`。
- 是否需要数据库备份取决于本次最终是否新增或有待执行迁移，不能只因涉及 CRM 源码就要求重做迁移。

## 残留风险与未验证边界

- API 全依赖审计保留 3 项 moderate（生产 2 项），对应 Nest 内置 SSE 的同一公告。当前源码没有 `@Sse()`/Nest `SseStream` 调用，使用自定义 JSON 序列化 SSE；据调用链判断本轮未发现该公告的可达入口。这不是漏洞不存在的保证；未来使用内置 SSE 前应升级并验证框架。[官方公告 GHSA-36xv-jgw5-4q75](https://github.com/advisories/GHSA-36xv-jgw5-4q75)
- 安装仍提示部分传递包弃用；没有通过强制主版本升级或批量批准安装脚本消除提示。干净安装验证覆盖当前需要的原生与运行依赖，但不能代替 Linux 服务器的部署验收。
- Web 构建仍有 Markdown 渲染懒加载块超过 500 kB 的提示，本轮没有为消除提示随意调整拆包或禁用功能。
- 浏览器回归使用虚构接口数据；真实 HTTP 回归使用编译后的 API 和本机隔离 MySQL。真实 CAS、钉钉、CRM 和模型供应商未在本次测试中调用，不能据此宣布完成生产联调。
